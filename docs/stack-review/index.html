AgenOS Stack and Program Review

This is an objective technical review of the current AgenOS repository as of 2026-05-14. The project is best described today as a Debian Bookworm live/installable image with a custom Wayland kiosk session, a guided Calamares wrapper, and an early Electron/React shell connected to a ChatGPT/Codex development harness. It is not yet a complete agentic Linux distribution.

Base: Debian 12 Bookworm Image system: live-build Session: greetd + Sway + Electron Installer: Calamares + Bun API UI: React 19 + Vite + Electron
Strong Buildable vertical slice, clear repo layout, typed UI services, useful tests.
Prototype The OS layer is mostly live-build includes, not a packaged distro product.
Critical Gap No real local agent, STT/TTS pipeline, policy engine, memory, or audited tools.
Hardening Needed Electron sandboxing, local API trust, privileged helpers, and supply chain are not production-grade.

Executive Summary

AgenOS has a coherent first slice. The repository can assemble a Debian live ISO, launch a Wayland session through greetd and sway, run a fullscreen Electron UI, expose installer/system APIs through Bun, and hand off selected installation data to Calamares. This is a meaningful prototype because it crosses the boundary from web UI into real OS actions.

The problem is the gap between the stated ambition and the current implementation. A state-of-the-art distro needs reproducible packaging, update channels, secure privilege separation, robust boot/session recovery, real accessibility primitives, local-first AI services, observability, test automation on real images, and a maintainable release process. AgenOS currently has several of those ideas represented, but mostly as scripts, wrappers, or placeholders.

Objective verdict: keep the direction, but stop treating this as a distro architecture until the project has first-class packages, signed releases, a real agent daemon, local speech, hardened IPC, and automated ISO/VM validation.

Runtime Flow

  1. make build builds the live-build Docker image and runs UI build scripts.
  2. The UI scripts run Bun builds, copy Electron, static assets, and wrapper scripts into build/live-build/config/includes.chroot.
  3. lb build creates the ISO from Debian package lists plus the custom include tree.
  4. At boot, live-config prepares the live user and greetd launches agenos-session.
  5. sway starts agenos-shell-runner, which chooses system or installer mode and launches Electron.
  6. Electron loads either the system shell by file or the installer shell via the local Bun API at 127.0.0.1:4173.
  7. Privileged operations cross into pkexec helpers, then into Calamares or system commands.

What Is Good

1. The project has a real vertical slice

The repo does more than render a mock UI. It discovers disks with lsblk, validates installer profiles, creates Calamares configuration, writes secure runtime files, starts privileged helpers, and configures the installed target for greetd and the AgenOS session. That makes it a useful platform for further OS work.

2. The installer wrapper is reasonably disciplined

The guided installer validates user, locale, keyboard, timezone, disk, install mode, and root mode before handoff. The profile is written with restrictive permissions, its path is constrained to the runtime directory, and the Calamares seeded module is explicit. This is the right shape for a safer custom installer path.

3. The UI/service separation is moving in the right direction

components/installer-ui/src/shared/system-services is a good architectural move. The same service concepts can be reused from Bun and Electron IPC, which reduces duplication at the boundary where OS actions live.

4. There is meaningful unit coverage

The repo has focused tests for disk discovery, preflight, profile validation, launch behavior, runtime state, switch-mode behavior, installer client behavior, UI behavior, speech recognition wrappers, and the ChatGPT/Codex harness. This is good for a prototype and much better than a pure shell-script distro experiment.

5. The session architecture is simple enough to debug

greetd + sway + fullscreen Electron is understandable, lightweight, and easier to reason about than a full desktop shell fork. The fallback/retry logic and GPU fallback notes show that the project has already encountered real VM/hardware instability and started to handle it.

What Is Wrong

1. This is not yet a maintainable distro

The current image is assembled by copying files into live-build/config/includes.chroot. That is acceptable for early prototypes, but it is not a production distribution model. There are no Debian packages for AgenOS components, no apt repository, no package upgrade path, no signed metadata, no split between source packages and generated runtime artifacts, and no rollback/update story.

2. The agent is essentially absent

components/agent is documentation only. The current "agentic" behavior is a UI harness around ChatGPT/Codex. There is no local daemon, no policy engine, no audited tool registry, no memory subsystem, no event stream, no local STT/TTS, and no system-level accessibility layer. For a voice-first distro, this is the largest missing subsystem.

3. The security model is too permissive for the ambition

  • Electron is launched with --no-sandbox, and the BrowserWindow disables Electron sandboxing.
  • The Bun API is bound to localhost, but it has no session token or origin-level authorization.
  • Local processes can call maintenance, installer, PI auth, PI chat, and shell mode routes if they can reach 127.0.0.1:4173.
  • Polkit rules approve active local users for helper actions without a finer permission split.
  • The installer Electron handler calls shell.openExternal(url) for any window-open URL, unlike the stricter system shell path.

The helper command surfaces are mostly whitelisted, which is good, but the overall trust boundary is still "anything in the active local user session is trusted." That is not enough for an agentic OS that may run untrusted documents, browsers, extensions, or model-generated actions.

4. Reproducibility and supply chain are weak

The Dockerfile installs Node from NodeSource, Bun from a remote install script, and Rust via rustup. The UI builds then copy Electron and Codex binaries from node_modules into the image. There is no SBOM, no artifact attestation, no ISO signing, no deterministic build claim, and no vulnerability scanning path. Release publishing uses SHA256 sums and Google Drive upload, which is useful for a class project but not a serious distro release channel.

5. There is drift and duplicated architecture

The docs say some parts are future placeholders while the code now packages a system shell. The live-system-slice document references files such as LiveSystemView.tsx and system-command.ts that are not present. There is also an old Python shell server under usr/local/lib/agenos-shell/server.py that appears no longer wired through the current launcher path. The PI harness exists in both components/ui/dev and components/installer-ui/src/bun, with different capabilities and TTL behavior.

6. Some code paths are inconsistent

The system UI can request startAuth("device") or startAuth("browser"). The dedicated system Electron harness supports that split, but the Bun API path in components/installer-ui/src/bun/server.ts ignores the posted auth method and calls an older startAuth() implementation. That kind of drift will produce environment-specific behavior and difficult debugging.

7. The product currently contradicts the accessibility goal

A voice-first accessible OS needs dependable speech input, speech output, keyboard-only operation, screen reader compatibility, large target modes, offline fallback, and clear recovery paths. Current speech is Web Speech API based in the UI and the docs still describe demo transcription in places. That is not enough for an accessibility-oriented operating system.

What I Would Implement Next

Milestone 1: Turn the prototype into a real distribution artifact

  • Create Debian packages for agenos-shell, agenos-installer-ui, agenos-agent, themes, policy files, and session config.
  • Stop copying built application directories into includes.chroot/opt as the primary architecture.
  • Add an apt repository, package signing, ISO signing, checksums, SBOM generation, and release provenance.
  • Separate source, generated build output, and image assembly so build state does not dirty the repo.

Milestone 2: Define and build the local agent daemon

  • Implement agenos-agent as a real service with a narrow local IPC API.
  • Use a typed event protocol for STT partials, final transcripts, intent proposals, confirmations, execution, and audit logs.
  • Make tools declarative: schema, risk level, required confirmation, allowed user/session, timeout, rollback note, and audit output.
  • Keep model/provider adapters behind the daemon. The UI should not own core agent state.

Milestone 3: Replace demo voice with local-first speech

  • Add local STT using whisper.cpp, Vosk, or another explicitly selected engine.
  • Add local TTS using Piper or an equivalent offline engine.
  • Route audio through PipeWire with explicit device selection, push-to-talk, wake mode, and privacy indicators.
  • Test microphone and speaker failure modes in the live image.

Milestone 4: Harden the shell and privilege boundary

  • Remove --no-sandbox where possible, enable Electron sandboxing, and enforce a strict Content Security Policy.
  • Add a session-bound token or Unix socket credential check to every local API route that can affect system state.
  • Split polkit actions by capability: installer launch, terminal, reload, poweroff, reboot, disk operations.
  • Log every privileged action with subject, command, arguments, result, and correlation ID.
  • Do not allow generic external URL opens from installer windows.

Milestone 5: Build real validation infrastructure

  • Add CI jobs for typecheck, unit tests, linting, package build, and ISO build smoke tests.
  • Add QEMU boot tests that verify login, shell startup, API health, installer launch, and installed-disk boot.
  • Add destructive install tests only against disposable virtual disks.
  • Record boot logs and screenshots as CI artifacts.

Recommended Direction

The best path is to keep Debian, live-build, Calamares, greetd, Sway, and the React UI for now, but move the OS-critical pieces out of ad hoc image includes and into packages. Treat Electron as a renderer, not as the authority. The authority should be a local agent/control daemon with a minimal, authenticated IPC surface and auditable tool execution.

Do not invest heavily in more visual polish until the architecture can safely answer these questions: who is allowed to trigger an action, how is the action confirmed, where is it logged, how does the system recover if it fails, how does it update, and how can the same image be rebuilt byte-for-byte or at least with verifiable provenance?

Final Verdict

AgenOS is a solid technical prototype and a good base for a thesis-scale proof of concept. It is not yet a state-of-the-art distro. The strong parts are the working ISO path, the guided installer slice, the Wayland kiosk direction, and the typed/tested service modules. The weak parts are the absence of a real agent, weak distro packaging, weak supply-chain guarantees, broad local trust, Electron hardening gaps, documentation drift, and duplicated runtime code.

The next serious step is not another UI screen. It is a production-shaped core: packages, signed images, authenticated IPC, a local agent daemon, offline speech, audited tools, and VM-backed verification.
